# Сравнение подходов к хранению достижений

Обязательный пункт кейса: «сравнительный анализ как минимум двух подходов».
Сравниваем по двум независимым осям, потому что это два разных решения:
**где живёт достижение** и **как паспорт узнаёт об изменениях**.

## Ось 1. Где живёт достижение

| Критерий | A. Централизованный профиль в БД | B. Только Verifiable Credentials / Open Badges у владельца | **C. Гибрид (выбран)** |
|---|---|---|---|
| Верифицируемость вне платформы | Нет: «верьте нам на слово» | Да: подпись проверяется без нашего сервера | Да: экспорт подписанного Open Badge 3.0 + страница /verify |
| Кто хранит | Платформа | Ребёнок в цифровом кошельке | Платформа; копию бейджа ребёнок забирает при экспорте |
| Подходит детям 4–17 лет | Да | Нет: кошелёк и ключи ребёнку не по силам | Да |
| Рекомендации и аналитика | Просто: всё в одной БД | Сложно: данных у платформы нет | Просто |
| Приём от 2 200 сторонних лагерей | Только через наш API, доверие не проверить | Стандартный формат, подпись лагеря | Стандартный формат на входе (L3) + упрощённый вход без подписи (L1) |
| Удаление по 152-ФЗ | Просто | Выданное у владельца не удалить, только отозвать | Удаление у нас + отзыв в списке статусов |
| Трудоёмкость в MVP | Низкая | Высокая (кошелёк, DID, обучение партнёров) | Средняя: подпись и /verify — около 3 чел.-недель |
| Риск для MVP 3–6 месяцев | Низкий, но не выполняет требование «верифицируемый» | Высокий | Средний |

**Вывод.** A не выполняет требование кейса о верифицируемости и переносимости, B не подходит детям
и усложняет удаление. Гибрид C берёт сильные стороны обоих: источник истины — PostgreSQL,
Open Badges 3.0 — формат подписи, экспорта и приёма от партнёров.

## Ось 2. Как паспорт собирается из событий

| Критерий | D. Периодическая агрегация (ночной ETL из БД модулей) | **E. Журнал событий паспорта + проекции (выбран)** | F. Event sourcing всей платформы |
|---|---|---|---|
| Свежесть паспорта | До суток | Секунды | Секунды |
| Нагрузка на модули | Тяжёлые выборки из чужих БД каждую ночь | Модули только публикуют события (уже делают это в RabbitMQ) | Все модули переписываются |
| История и «уровень на дату» | Только снимки | Полная: журнал + SCD2 в child_skill | Полная |
| Пересчёт при смене правил навыков | Невозможен для прошлого | Повторное проигрывание журнала | Повторное проигрывание |
| Приём от партнёров | Нужен отдельный канал | Тот же конвейер: Partner API публикует события | Тот же конвейер |
| Право на удаление | Просто | Конфликт с неизменяемым журналом → решается crypto-shredding | Тот же конфликт, но во всех сервисах |
| Связность с чужими схемами | Высокая: ETL ломается при изменении схемы модуля | Низкая: контракт — AsyncAPI-схема события | Низкая |
| Трудоёмкость в MVP | Низкая | Средняя | Недостижима за 6 месяцев |

**Вывод.** E: event sourcing только внутри домена паспорта. Он даёт историю и пересчёт навыков
без переделки чужих модулей. Конфликт с правом на удаление закрывается шифрованием журнала
ключом ребёнка (см. privacy/deletion.py и тест `test_full_deletion_including_backups`).
